## 1. 是否先用 Tauri 命令初始化再写文档？

### 结论：**先写文档，再初始化脚手架（推荐）**

当前仓库几乎为空（仅 README），且产品含 **双棋种 + 人机 AI + 规则在 Rust** 等结构性选择。这些应先落在需求/架构里，再执行 `create-tauri-app`，否则容易出现：

| 先脚手架再文档 | 先文档再脚手架 |
|----------------|----------------|
| 模板目录已定，文档被迫迁就 | 文档约定目录，初始化时按约定微调 |
| 前端框架在未讨论时已锁定 | 在决策表中显式选定再生成 |
| 双棋种/crates 边界事后补丁 | 架构已预留 `games/` 或 workspace |
| 文档与真实树不一致需返工 | M0 任务变为「按文档 init」 |

### 何时可以「先 init」？

仅当以下都成立时，可先脚手架：

- 技术选型已口头/书面锁定（框架、包管理器、TypeScript 等）  
- 只需要空白可运行壳，文档写「现状」而非「目标」  
- 能接受随后按架构文档搬迁目录  

**本项目不满足「先 init」的前提**（选型与双棋种边界尚未在仓库中固化），故本次已直接产出 `docs/`，**尚未**执行 Tauri 初始化。

### 建议的下一步（M0）

文档评审通过后，在仓库根目录执行（示例，以当时 CLI 交互为准）：

```bash
# 推荐：官方创建器（Tauri 2）
npm create tauri-app@latest .
# 或
cargo create-tauri-app
```

交互选项建议与下文选型一致。若目录非空（已有 `docs/`、`README.md`），按 CLI 提示在当前目录创建或先确认覆盖策略；必要时先 init 到临时目录再合并，**保留 `docs/`**。

本机已检测到：`tauri-cli 2.11.4`、`node`/`npm`、`cargo`/`rustc`，具备立即脚手架的条件。

## 2. 技术选型（建议）

| 决策点 | 建议 | 理由 |
|--------|------|------|
| 应用框架 | **Tauri 2.x** | 轻量桌面、Rust 后端适合规则/AI |
| 前端 | **React + TypeScript + Vite** | 官方模板成熟、组件化适合双棋盘 UI |
| 包管理器 | **pnpm** 或 npm | 团队习惯优先；无强偏好时用 npm 降低摩擦 |
| UI 样式 | 轻量 CSS / 自研棋盘样式 | 棋盘为主视觉，避免重型组件库 |
| 状态（前端） | 页面局部 state + 对局 store（轻量） | MVP 不必上复杂全局方案 |
| 规则与 AI | **Rust**（`src-tauri` 或 `crates/*`） | 性能、可测、防前端篡改局面 |
| 象棋 AI | Alpha-Beta + 简单评估 | 实现成本与可玩性平衡 |
| 军棋 AI | 启发式 / 信息不完全搜索简化版 | 暗棋特性不适合照搬象棋搜索 |
| 军棋规则范围 | **二人翻棋 MVP（已确认）** | 2026-08-13 产品确认；传统布局模式为 P2 |
| 持久化 | MVP 不做；二期 `tauri-plugin-store` | 聚焦对局闭环 |
| 测试 | Rust `cargo test` 为主 | 规则正确性优先 |
| CI | 后续再加 `cargo test` + 前端 typecheck | M0–M1 本地验证即可 |

### 备选（明确不选的原因）

| 选项 | 态度 |
|------|------|
| Electron | 包体更大；规则仍可用 WASM/原生，但与「Rust 一体」目标不符 |
| 纯前端规则引擎 | AI 与防篡改弱；与需求 N-05 冲突 |
| Vue/Svelte | 可行，但无团队偏好时跟 Tauri 最常见 React 模板 |
| 外挂专业象棋引擎 | 远期可选；MVP 自研浅层搜索即可 |
